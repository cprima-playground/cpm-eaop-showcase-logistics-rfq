## Headline finding

**This repository contains zero live GCP integration.** No GCP SDK imports,
no `google-cloud-*` direct dependencies, no `google.auth`/ADC calls, no
Terraform `google` provider, no `gcloud` invocations, no Cloud Build config,
no CI/CD at all (`.github/` does not exist). Every GCP reference is
**target-state prose** in `deploy/`, `decisions/`, and
`data/env/environments.yaml`. The running implementation is Docker Compose +
Keycloak + Entra (azuread Terraform) + HashiCorp Vault + Cedar PDP + OTel,
all local.

Verification: repo-wide grep for `google.cloud|google.auth|google.oauth2|
googleapiclient|gcloud|googleapis.com|vertexai|aiplatform|GenerativeModel|
google.genai|google.adk|GOOGLE_APPLICATION_CREDENTIALS|secretmanager|
K_SERVICE|resource "google_"`. The only Python `google` import in the
entire tree is `from google.protobuf import json_format`
(`src/rfq_common/rfq_common/a2a_context.py:11`, protobuf JSON helper, not a
GCP API). `google-auth`/`google-api-core` appear only as transitive `uv.lock`
entries (pulled by `a2a-sdk`'s gRPC stack), never imported.

*Note: this finding predates the `spikes/hello-agent-adk` and

[Update](#update-2026-07-31-later) below.*

## 6. Gaps (at time of this scan)

**Implementation gap** (largest): every GCP building block was
documentation only — no GCP Terraform, no `infra/cloudbuild/`, no Secret
Manager client, no WIF credential configuration, no Vertex/ADK/Gemini code,
no Firestore adapter, no Cloud Run service definitions. Dev LLM was `stub` —
no LLM inference of any kind was exercised.

**Permission gap:** unquantifiable — no GCP operation was concrete enough to
name a permission. All entries above `NEEDS GCP VERIFICATION`.

**Availability gap:** Vertex AI Agent Engine and Apigee were the two
highest-risk assumptions, neither corroborated by an executable artifact.

**Evidence gap:** "this showcase demonstrates GCP-hosted agentic
governance" was not supported at scan time. What it demonstrably proved:
IdP-federated machine identity, Cedar PDP/PEP separation, env-conditional
secret storage, A2A/MCP chaining, OTel observability — all portable and
GCP-neutral. The repo's GCP coupling was a *hosting choice*, not an API
dependency.

## Update, 2026-07-31 (further)

- **WIF federation exists, but not to Entra.** Checked directly:
  `cpm-geap-2026` has a real, active Workload Identity Pool
  (`external-apps`) with one active provider, `keycloak` — issuer
  `https://cpm-eaop-keycloak-dev.jerm.uk/realms/agents`,
  `google.subject: assertion.azp`, allowed audience `control-panel-svc`.
  **No Entra provider exists on this pool or anywhere in the project.** The
  "GCP↔EntraID federation" this report and ADR-006 describe is still purely
  declared intent — what's actually configured is GCP↔Keycloak.
- **That Keycloak issuer is a Cloudflare Tunnel, and it's currently down.**
  `cpm-eaop-keycloak-dev.jerm.uk` resolves to Cloudflare anycast IPs and
  returns HTTP 530 (tunnel/origin unreachable) as of this check — the
  tunnel client isn't running or the local Keycloak container is down. **Its
  configuration is not tracked in this repo** (no `cloudflared` config, no
  `jerm.uk` reference anywhere in `infra/` or docs) — an untracked, personal
  dependency the WIF setup currently relies on.
- **Federation itself has no cost.** Workload Identity Pools, providers, and
  token exchange (`sts.googleapis.com`/`iamcredentials.googleapis.com`) are
  free; only what a federated identity subsequently *uses* (Cloud Run,
  Vertex AI inference, Secret Manager calls, egress, etc.) is billed.
- **`spikes/hello-agent-adk`'s OTel warnings, found and fixed.** Cloud
  Logging for the Agent Engine resource showed:
  ```
  WARNING: telemetry enabled but proceeding without gRPC instrumentation, because opentelemetry-instrumentation-grpc has not been installed
  WARNING: telemetry enabled but proceeding without httpx instrumentation, because opentelemetry-instrumentation-httpx has not been installed
  WARNING: telemetry enabled but proceeding without Google GenAI instrumentation, because opentelemetry-instrumentation-google-genai has not been installed
  ```
  Agent Engine has telemetry enabled by default; the spike's `REQUIREMENTS`
  only listed the base `aiplatform` package (a regression from `cpm-eaop`'s
  original, which had `opentelemetry-instrumentation-httpx` — dropped when
  simplifying, and the grpc/google-genai instrumentors were never added
  either). Fixed by adding all three to `spikes/hello-agent-adk/deploy.py`'s
  `REQUIREMENTS` and redeploying via `agent_engines.get(...).update(...)`
  (same resource, not a new one). Verified: re-triggered the agent, checked
  Cloud Logging for 5 minutes post-redeploy, zero instrumentation warnings.
  `spikes/hello-mcp` has no OTel instrumentation at all yet (not flagged by
  the platform the way Agent Engine's default-on telemetry flags Agent
  Engine — Cloud Run doesn't auto-warn about missing tracing) — worth
  addressing if these spikes are meant to exercise observability products
  deliberately, per the stated intent to spike "many if not all" related
  GCP products, not stay minimal.

## Update, 2026-07-31 (Terraform onboarding)

Both spike resources are now Terraform-managed (`infra/terraform/` in this
repo, scoped to this repo + `cpm-geap-2026` only — `cpm-eaop`'s own
Terraform/state deliberately untouched):

- `google_vertex_ai_reasoning_engine.hello_agent_adk` — this resource type
  did **not** exist in this project's originally-installed `google` provider
  (6.50.0, matching `cpm-eaop`'s pinned version); confirmed absent by
  checking the provider's actual GitHub source/changelog, not assumed.
  Upgrading to `~> 7.42` (current) resolved this — the resource has existed
  in the provider for a while, it just predates our checked version.
- `google_cloud_run_v2_service.hello_mcp` + its
  `google_cloud_run_v2_service_iam_member` (the `--allow-unauthenticated`
  binding) — both onboarded via `terraform plan -generate-config-out` +
  `terraform import`, not hand-authored, so the `.tf` reflects what was
  actually deployed rather than a guessed spec.

`terraform plan` shows zero drift post-import for all three resources. This
closes the "unmanaged shadow infra" gap this report originally flagged for
these two spikes specifically (Agent Engine deploys in general remain
provider-version-dependent for anyone using an older `google` provider
pin — worth checking before assuming the gap still exists elsewhere).
